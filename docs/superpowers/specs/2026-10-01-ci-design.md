# Continuous integration — design

Date: 2026-10-01
Status: implemented
Branch: `ci/github-actions`, based on `feat/test-api-alignment` (PR #6)
Depends on: PR #6 (on `main` today, `tsc` reports errors and every browser test fails on Firefox 157's privileged `about:home`)

## Goal

Every push to `main` and every pull request runs the typecheck, the unit tests, the browser tests and Trunk's code quality checks on GitHub Actions, using bun.

## Non-goals

- ESLint. Code quality checks come from Trunk (below), which runs the linters configured in `.trunk/trunk.yaml`.
- Trunk on the whole repository (`trunk check --all`): existing files are not all formatted yet; CI checks only what a change touches.
- A macOS or Windows runner. Linux finds the same protocol bugs at a tenth of the macOS minutes.
- Test coverage reports, caching tuned beyond what `setup-bun` does, release or publish jobs.
- Pinning the Firefox version (see Risks).

## Decisions

- **bun, not npm.** `bun install --frozen-lockfile` and `bun run <script>`; `bunx` for one-off binaries. The package scripts are unchanged: `bun run test` still runs `tsx --test` on Node's test runner. CI does not switch to `bun test`.
- **Node is still installed.** The scripts run `tsx`, which runs on Node, and the runner uses `fs/promises` `glob` (Node 22+). CI pins Node 26, the version the code is developed against.
- **Four parallel jobs** instead of one job with four steps: a failure names the broken check, and the checks don't wait on each other.
- **Trunk checks changed files only.** The same `.trunk/trunk.yaml` drives the local pre-commit/pre-push hooks and CI, so it is committed (with Trunk's own `.trunk/.gitignore` and `.trunk/configs/`).

## Workflow — `.github/workflows/ci.yml`

### Triggers

```yaml
on:
  push:
    branches: [main]
  pull_request:

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}

permissions:
  contents: read
```

A new push to a pull request cancels that pull request's run in progress; runs on `main` always finish. The workflow only reads the repository.

### Shared setup (`typecheck`, `unit`, `browser`)

1. `actions/checkout@v4`
2. `oven-sh/setup-bun@v2` with `bun-version: 1.3.0` (the local version)
3. `actions/setup-node@v4` with `node-version: 26`
4. `bun install --frozen-lockfile` — fails when `bun.lock` and `package.json` disagree

Each job runs on `ubuntu-latest`.

### Jobs

| Job id      | Name                    | Command                                          | `timeout-minutes` |
| ----------- | ----------------------- | ------------------------------------------------ | ----------------- |
| `typecheck` | Typecheck               | `bunx tsc --noEmit -p .`                         | 5                 |
| `unit`      | Unit tests              | `bun run test`                                   | 10                |
| `browser`   | Browser tests (Firefox) | `firefox --version`, then `bun run test:browser` | 15                |
| `trunk`     | Code quality (Trunk)    | `trunk-io/trunk-action@v1`                       | 15                |

- The browser job uses the Firefox preinstalled on `ubuntu-latest`; the framework finds it with `which firefox`.
- `firefox --version` is its own step so the log shows which Firefox ran.
- `timeout-minutes` stops a hung browser run instead of holding a runner for the default 6 hours.
- The browser test step has its own 12-minute timeout so a hang fails the step and the logs are still uploaded.

### The `trunk` job

- Steps: `actions/checkout@v4`, then `trunk-io/trunk-action@v1`. It installs the Trunk CLI and the linter versions pinned in `.trunk/trunk.yaml` itself; no bun or Node setup.
- On a pull request it checks only the files the PR changes; on a push to `main`, only what the push changed. Findings appear as annotations on the changed lines.
- It needs `checks: write` (job-level `permissions`, on top of the workflow's `contents: read`) to publish those annotations.
- Linters enabled today: prettier, markdownlint, yamllint, svgo, git-diff-check, and the security scanners checkov, trufflehog, osv-scanner and grype. Changing that list is a change to `.trunk/trunk.yaml`, not to the workflow.

### When a job fails

The browser job uploads the framework's logs and the report:

```yaml
- if: failure()
  uses: actions/upload-artifact@v4
  with:
    name: browser-test-logs
    path: |
      logs/
      result/
    retention-days: 7
    if-no-files-found: ignore
```

`logs/combined.log` holds the BiDi traffic, which is how browser failures are diagnosed. Test secrets in CI are fake values, and the logger masks registered secrets.

## Risks

- **Firefox version drift.** `ubuntu-latest` installs Firefox from a PPA; its version can differ from the local Firefox 157, so a browser test can pass locally and fail in CI or the reverse. Mitigation: the version is logged; if a version-specific failure appears, pin it with `browser-actions/setup-firefox` in a follow-up.
- **Headless Firefox on Linux** has no display; the browser tests already launch with `headless: true`.
- **Trunk on changed files** can still flag pre-existing problems in a file a PR touches (e.g. formatting of lines the PR did not change). The PR then formats that file; the local `trunk fmt` pre-commit hook does this automatically.

## Verification

- `ci.yml` is valid YAML and passes `actionlint` (run with `bunx` or the `rhysd/actionlint` Docker image if available locally; otherwise the first GitHub run is the check).
- The commands each job runs pass locally with bun: `bun install --frozen-lockfile`, `bunx tsc --noEmit -p .`, `bun run test`, `bun run test:browser`.
- `trunk check` passes locally on the files this branch changes.
- After pushing the branch and opening a PR against `feat/test-api-alignment`, all four jobs are green on GitHub. A failing check is diagnosed from the run log (and the artifact for the browser job), not guessed.
