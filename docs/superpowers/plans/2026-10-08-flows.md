# Flows in the framework Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `samurai flow run <flow>` runs a SAMURAI flow headlessly from a project folder, validated the same way the app validates it, with exit codes and a report file. The framework owns the flow file format, node kinds, validation, expressions and execution; the app (separate repo) only edits and shows flows.

**Architecture:** A new `src/flows/` tree with two halves. `flows/core` is pure TypeScript (no `node:` imports, safe for a browser bundle): file format, keys, graph helpers, the expression language, node core definitions, `checkFlow`. `flows/run` is Node: handlers per node kind, a shape-driven walker, project loading (flow files, tests, groups), events and summary. `groups` in the config is implemented first because flows resolve Group nodes through it. The CLI gains `samurai flow list | check | run`.

**Tech Stack:** TypeScript (ESM, `nodenext`), Node's test runner via `tsx --test`, `node:assert/strict`, existing runner (`runTests`, `listTests`), bun for scripts.

**Spec:** `docs/superpowers/specs/2026-10-08-flows-in-the-framework-design.md` (copied from the app repo, where its migration steps 5 to 7 are tracked). This plan is migration steps 1 to 4. The app repo's current implementation (`src/shared/flows/`, `src/engine/flow/` in `../samurai`) is the source to port from.

## Global Constraints

- Match the repo: ESM with `.js` import suffixes, `node:test` + `node:assert/strict`, tests as `*.test.ts` next to the code, browser tests as `*.browser-test.ts`, CLI tests as `*.cli-test.ts`. Never `bun test`; use `bun run test`.
- `flows/core` imports nothing from `node:*`, `src/runner`, `src/browser`, `src/config` or `winston`. Task 3 adds a test that enforces it.
- Code ported from the app keeps its behaviour and error messages exactly; only the test runner (`bun:test` to `node:test`) and import paths change. Port each test file with its module.
- Messages shown to people (check problems, node errors) are the app's current strings; the app's tests pin several of them.
- Never run `bun run dev` / `src/index.ts` / `src/tests/index.spec.ts`: the example spec submits a real contact form.
- A Trunk pre-commit hook formats staged files and a pre-push hook runs `trunk check`; let them run, and commit what they format.
- Commit messages end with `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>`. Stage only the files a task names; never `git add -A`.
- Work on a new branch off `main` (the current branch, `feat/press-step`, is unrelated). Tasks 1 to 3 merge without a version bump; Task 6 bumps the minor.
- `bun run build` must keep producing the new entry points; `bun run test`, `bunx tsc --noEmit` pass after every task.

## Review Focus

1. **A browser-unsafe import creeping into `flows/core`** — the app's renderer would break at build time, not in the framework's tests. Pinned in Task 3 (purity test over the import graph and a bundle check).
2. **Group resolution differing from the app's** — a flow would run other tests in CI than it did locally. Pinned in Task 1 (ported cases: picked tests, `src`, `testMatch`, missing picked tests).
3. **Test ids differing from the app's** — Test nodes store `file::name` with the file relative to `srcDir`, posix separators. Pinned in Task 1 Step 1 (`testId`) and Task 5 Step 3.
4. **The walker special-casing a kind** — the point of shapes. Pinned in Task 5 Step 1 (a fixed-branch kind defined inside the test runs with no walker change).
5. **A skipped node making a CI run green** — Pinned in Task 4 (`checkFlow` reports unsupported kinds) and Task 6 Step 2 (`run` refuses to start; `--allow-unsupported` is the only way to skip).
6. **Cancellation leaving no report** — Pinned in Task 6 Step 4 (SIGINT writes a cancelled report, exit 1).

### Task 4: Node core definitions and `checkFlow`

**Files:**

- Create: `src/flows/core/nodes/{define,index,start,end,test,group,condition,parallel,wait,set-variable,api,database,email,script}.ts`, `src/flows/core/check.ts`, tests

**Interfaces:**

- Produces: `NODES`, `nodeDef(kind)`, `NodeCoreDefinition` (`kind`, `label`, `shape`, `branches`, `fields`, `outputs`, `onFailure`, `validate`), `checkFlow(flow, ctx)` returning `FlowProblem[]`. The app's editor definitions wrap these.

- [ ] **Step 1: Core definitions**

  Port from `../samurai/src/renderer/src/lib/flows/nodes/` only the data half of each kind: `kind`, `label`, `shape`, `branches` (the `{ name, label?, color? }` form and `{ dynamic, min }`), `fields` as data (type, path, label, default, options; no React components, no icons, no `section`), `outputs`, `onFailure`, `validate`. `api`, `database`, `email`, `script` are declared here too and have no handler (unsupported). - [ ] **Step 2: `checkFlow`**

**Interfaces:**

- Produces: `runFlow(options)`, `runFlowInProject(options)`, `readFlows(projectDir)`, `FlowEvent`, `FlowSummary`, `NodeResult`, `Handler`, `HANDLERS`. Task 6 and the app's engine consume them.

- [ ] **Step 1: Walker by shape**

  Port `../samurai/src/engine/flow/run.ts` and `handlers.ts` with their tests (`run.test.ts`). Replace the `node.kind === "condition" | "parallel" | "end"` checks with shape lookups through `nodeDef(kind).shape`: `branches` fixed list uses the handler's `branch`; dynamic lists walk branches in fill order; `end` shape stops. Add the guard test: every core kind is either in `HANDLERS` or in an explicit `UNSUPPORTED` list, and every handler has a core kind. - [ ] **Step 2: Events and summary**

  `events.ts` exports `FlowEvent` (`flow-start`, `node-start`, `node-end`, `test`, `flow-end`), `FlowSummary`, `NodeResult` exactly as in `../samurai/src/shared/flows/runtime.ts` (the app reads these).

- [ ] **Step 3: Project loading**

### Task 6: The `samurai flow` command

**Files:**

- Create: `src/flows/run/report.ts`, `src/cli/flow.ts`, `src/cli/flow-reporter.ts`, `src/cli/flow.cli-test.ts`, `docs/flows.md`
- Modify: `src/cli/args.ts`, `src/cli/main.ts`, `docs/cli.md`, `docs/embedding.md`, `README.md`, `package.json`

- [ ] **Step 1: Arguments**

  `samurai flow list | check [<flow>...] | run <flow>... | run --all`, with `--allow-unsupported` and the existing `--env`, `--headless`, `--timeout`, `--expect-timeout`, `--port`, `--json`. A flow is an id or a path. Unknown flags stay errors. Tests in `args.test.ts`.

- [ ] **Step 2: check and run**

  `check` prints each problem with the node's key and title; exit 0 without errors, 1 with errors, 2 for usage or unreadable files. `run` checks first and refuses to start on errors (exit 2, nothing executed). Unsupported kinds are errors unless `--allow-unsupported`. `--all` runs every flow in file name order; exit 1 if any failed; every flow writes its own report.

- [ ] **Step 3: Output and report**

  `flow-reporter.ts`: the human output from the spec (✔ ✖ ◇ ⊘ lines, a summary line with passed/failed/skipped/not run counts), colour rules as `ConsoleReporter`. `--json` prints one `FlowEvent` per line. `report.ts` writes `result/flows/<id>.json` (`FlowSummary` plus per-test results from the runner's events, secrets masked like `report.json`).

- [ ] **Step 4: Signals**

  SIGINT/SIGTERM abort the current run through the existing `io.signal`; the run ends `cancelled`, the report is still written, exit 1. CLI test: abort mid-flow and read the report.

- [ ] **Step 5: Docs, version, verify, commit**

  `docs/flows.md` (format, nodes, expressions, `check`, `run`, exit codes, report, unsupported kinds, a GitHub Actions example next to the existing CI one), update `docs/cli.md`, `docs/embedding.md` entry points table, README. Bump the version to the next minor in `package.json`. `bunx tsc --noEmit`, `bun run test`, `bun run test:cli`, `bun run test:browser`, `bun run build`. Commit `feat: samurai flow command`.
