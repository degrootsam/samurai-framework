## TL;DR

1. **0.15.1** is the release where retries really ship. 0.15.0 on npm was built before the retries commit and has no retry code. Your PR #33 heads-up was right. Since #53, `prepack` rebuilds `dist/` before every pack, so this can't happen again.
2. **0.15.1**: `parseSpec` now returns `test.skip(...)`, `test.fixme(...)` and `test.only(...)` tests with their steps and a `modifier`. The editor can show and edit them.
3. **0.15.2**: skip and fixme take an optional `{ reason }`. The reason shows up in results, `listTests` and `parseSpec`.
4. Roadmap: the "Engine process" item is gone. It is replaced by **stable `listTests`, `listGroups`, `parseSpec` and recorder options across versions**, which the framework is starting on now. Please don't add new version shims for these four in the meantime. See section 4.
5. **Your hand-off (`samurai/docs/handoffs/2026-10-21-framework-api-for-app.md`), items 1, 2, 3, 4 and 7, ships in 0.16.0** (PRs #58–#62, merged). Section 5 has what to code against. Items 5 and 8 need no framework work for now; item 6 is not started.

## 1. Retries (0.15.1)

There is no API change from what the 0.15 hand-off described: `retry`, `flaky` and `previousAttempts` on results, and one `test-start` per attempt. They only appear when running against framework 0.15.1 or later. Projects pinned to exactly 0.15.0 will never show retries.

## 2. `parseSpec` reads skipped and focused tests (0.15.1, PR #55)

- `parseSpec(source)` now returns every test that `listTests` lists, in source order, including `test.skip/fixme/only(title, fn)`.
- New field `ParsedTest.modifier?: "skip" | "fixme" | "only"`. It is set the way the runner sets it: a `describe` modifier counts, the innermost `skip` or `fixme` wins, and a skip beats a focus.
- `test.skip(condition, reason)` inside a body is a `custom` step of that test, not a test.
- Editing a skipped test changes only the touched statement. The `test.skip(` line stays.
- **Index shift.** In a file with such tests, the index of later tests moves up. Anything addressing tests by index (`applyEdit`'s `test`, `samurai record --test <n>`) must re-read the index after parsing. Looking tests up by `name` is unaffected.

What this means in the app:

- The app imports the codec in the main process from its own copy (`specs.ts`, `delete-tests.ts`, `secrets.ts`), not from the project's. With the app on 0.15.2, the test editor gets steps for `test.skip/fixme/only` tests in every project, whatever framework the project has.
- `src/main/utils/specs.ts` `parseSource` maps only `name` and `steps`. Pass `modifier` (and `reason`, below) through if the editor should show them.
- `src/main/utils/delete-tests.ts`: already handled in app PR #37, which moved to 0.15.2 for this.
- The steps panel's "No steps yet" will now also show for a skipped test with an empty body. That is correct.

## 3. `{ reason }` on skip and fixme (0.15.2, PR #56)

```ts
test.skip("checkout v2", { reason: "waits for the new payments API" }, async ({ page }) => {});
test.fixme("search", { reason: "flaky on staging" }, async () => {});
describe.skip("Old", { reason: "replaced by v2" }, () => { /* tests */ });
describe.fixme("Payments", { reason: "flaky on CI" }, () => { /* tests */ });
```

- Optional. The two-argument forms are unchanged. `TestDetails` (`{ reason?: string }`) is exported from the package root.
- A test gets the reason of the skip or fixme that applies to it: its own, else the closest `describe` around it. Example: `test.fixme("b", { reason: "own" })` inside `describe.skip("Old", { reason: "replaced" })` ends up as `fixme` with `"own"`.
- Where it appears:
  - **Results / events / `result/report.json`:** a skipped `test-end` result has `reason`. This field existed before, but only came from `test.skip(condition, reason)`. `src/main/runs/test-events.ts` already copies it, and `test-result.tsx` and `timeline-node.tsx` already show it, so no change is needed there.
  - **`listTests`:** `{ name, file, modifier?, reason? }`. `ProjectTest` in `src/shared/projects.ts` has no `reason` yet. Add it and show it on the `ModifierBadge` (a tooltip, for example) in `tests-table.tsx` and `group-tests-table.tsx`.
  - **`parseSpec`:** `ParsedTest.reason`, only when the reason is written as a string literal (a variable is not read).
  - **CLI:** `samurai list` prints `name [fixme: reason]`, and `--json` has `reason`.
- `test.skip("title", { reason })` without a function now throws `test.skip("title") needs a function as its last argument` at import. Before, it registered a test with no body.
- **Not supported:** the codec has no edit for the reason, or for adding or removing a modifier. `applyEdit` only edits steps. If the UI wants to toggle skip or edit the reason, that needs a new codec op from the framework. Ask for it rather than rewriting the call in the app.

## 4. Roadmap: stable listTests, listGroups, parseSpec and recorder options

The "Engine process" item (a framework-provided child process) is removed. The app's own engine (`src/engine/index.ts` plus `src/main/engine/client.ts`) stays the engine. The wiki's Embedding page now describes it.

New item, which the framework is starting on now: **stable `listTests`, `listGroups`, `parseSpec` and recorder options across versions.** The goal is a shape that stays the same from one version to the next, so the app can stop checking feature by feature.

`parseSpec` has no shims today because the app uses its own copy of the codec. It is in the item because a spec written for a newer framework than the app's copy may hold forms the app's codec doesn't know. A stable shape lets the app load the codec from the project's copy too.

### Item 2: test ids (#59)

`listTests` now returns `{ id, name, file, relativeFile, modifier?, reason? }`.
- `relativeFile` is the spec path relative to the real `srcDir`, with `/` separators.
- `id` is `<relativeFile>::<full name>`, built by the same function that fills `ResolvedGroup.testIds`, so `FoundTest.id` always matches group membership, including through a symlinked project folder.

### Item 3: whole tests in the codec (#60, no capabilities key)

No key, because the app runs the codec from its **own** bundled copy (`@itmetsam/samurai-framework/steps` in the main process). Gate on the app's dependency version, not on the project.
- `ParsedTest.start` / `end`: the whole `test(...)` statement. `start` is TypeScript's full start, so it includes the comments above the test and the blank line before it. That is exactly what `removeTests` cuts today.
- `applyEdit(source, { op: "remove-test", test })` removes that range and leaves everything else byte for byte. It throws when `ParsedTest.removable` is `false`: the test call isn't a statement of its own (a `for`/`if` body without braces, or an arrow's expression body like `[].forEach(() => test(...))`). Removing it would leave invalid TypeScript. Your current `removeTests` has the same flaw on older frameworks, so check `removable` (or catch the error) and tell the user. To remove several tests, apply the edits from the highest index to the lowest. Your four `delete-tests.test.ts` cases are ported into the framework and give identical output, so `removeTests` can become a name → index lookup plus `applyEdit` calls.
- `parseSpecFile(source)` returns `{ tests, unparsed }`; `parseSpec` is still `parseSpecFile(source).tests`. Each `unparsed` entry is `{ kind: "test" | "describe", start, end, reason: "dynamic-title" | "not-inline" }`: the title is built in code, or the function isn't an inline block (a variable, an import, `async () => doThing()`). Compare `listTests` against `tests` and use `unparsed` to explain the difference instead of saying "couldn't find".
- **Behaviour change:** an unreadable `describe` is one `unparsed` entry, and the tests inside it are no longer returned. Before, they came back with names missing the describe title. `test.skip(condition, reason)` inside a body is neither a test nor unparsed.

### Item 4: resolved config (#61)

```ts
import { loadConfig, type ResolvedConfig } from "@itmetsam/samurai-framework/project";
const config = await loadConfig({ projectDir, env: process.env }); // the engine registers tsx first, as today
```

The result is plain JSON, safe for `process.send`. Every default is applied using the constants the runner uses:
- **Paths:** `projectDir`, `srcDir` (absolute), `srcDirRelative`, `downloadsDir`, `filesDir`
- **Browsers:** `browsers` (always a list), `browserPaths`
- **Timeouts:** `timeout`, `expectTimeout`, `navigationTimeout`, `waitUntil`, `bidiCommandTimeout`
- **Running:**
  - `workers` (as written) and `workersResolved` (what a run without `--workers`/`SAMURAI_WORKERS` uses)
  - `retries`, `forbidOnly`, `headless`, `viewport`
- **Logs and network:**
  - `logs: { capture, failOnPageError, ignoreErrors: { text, regexp, flags? }[] }` (a `RegExp` becomes `{ text: source, regexp: true, flags }`)
  - `network: { track, idleTime, routeTimeout, collectBodies, maxBodySize }`
- **Environments:**
  - `baseURL?` and `defaultEnvironment?`, as written
  - `environments`: each `{ baseURL?, timeout, expectTimeout, headless, variables }`, merged with the same code a run uses. A config without environments has one, named `"default"`.
  - `environmentProblem?`: the message a run without `--env` would throw (several environments and no default, or an unknown `defaultEnvironment`). `loadConfig` does **not** throw for this.
- **Groups and steps:** `groups` (as written, plus each group's resolved `browsers`), `steps` (the kinds of the project's own flow steps)

An invalid config (bad `workers`, `browsers` and so on) throws the same error a run throws. Note: `forbidOnly` follows the runner's rule, which treats any set `CI` as CI (even `"0"`). `headless` uses the stricter rule, where `"0"` and `"false"` are not CI. The resolved config mirrors that mismatch instead of hiding it.

## 6. Answer to your reply (`2026-10-21-app-reply-to-framework-0.16.md`): 0.17.0

Both framework asks from your section 3 ship in **0.17.0** (PRs #66 and #67). Each has its own capabilities key.

### 3.1 The config as written: `writtenConfig`

```ts
import { loadConfig } from "@itmetsam/samurai-framework/project";
const { written, resolved, error } = await loadConfig({ projectDir, env: process.env, written: true });
```

- `written` is the config as the file states it, as plain JSON with nothing filled in. An absent `workers` stays absent, and a config without `environments` has none. `logs.ignoreErrors` patterns become `{ text, regexp, flags? }`, as in `resolved`, and `steps` become their kinds.
- **An invalid config doesn't throw in this mode.** `resolved` is left out and `error` holds the message a run would throw, so Settings can still show the file and the user can fix it. Plain `loadConfig(...)` without `written` still throws, as in 0.16.
- `writtenConfig(config)` does the same conversion for a config object you already have. Types: `ConfigViews`, `WrittenConfig`.
- With this, the engine's `readConfig()` can become `loadConfig({ written: true })`, with `written` for the fields and `resolved` for the "default: …" hints.

### 3.4 A results folder per run: `outputDir`

- `runTests({ ..., outputDir })` and `runFlowInProject({ ..., outputDir })` write `report.json` and the named screenshots to `outputDir` instead of `<project>/result`. A relative `outputDir` resolves against the project folder.
- Screenshot `path`s in results, events and the report are relative to `outputDir`, so with your run folder the app can drop its copying in `src/main/runs/screenshots.ts`.
- `reportPath` still wins for the report (`false` writes none). Worker processes get `outputDir` too.
- Not moved: generated files (`result/files`, removed when the run ends), downloads (`downloadsDir` in the config), and the CLI's flow report (`result/flows/<id>.json`; `runFlowInProject` writes no report itself).

### 3.2 and 3.3

No framework change. Compare against `editConfig` / `hasConfigPath` / `propertyText` and `setSecret` / `SECRET_NAME` in `./project` and send back what's missing.

## 7. Answer to your follow-up after 0.17.0: a folder per flow node (0.18.0)

- `runFlowInProject({ outputDir })` gives every Test and Group node its own folder: `<outputDir>/nodes/<node id>/` (the id cleaned to letters, digits, `-` and `_`). A node runs at most once per flow run, so two nodes never share a folder, even when they run the same test.
- Screenshot `path`s in a node's results are relative to **that node's folder**. Every flow `test` event carries `nodeId`, so the file is `<outputDir>/nodes/<nodeId>/<path>`.
- Pooled flows (workers > 1) do the same through `WorkItem.outputDir`.
- `runTests({ outputDir })` is unchanged: one folder, paths relative to it.
- Capability: `flowNodeFolders`. With it, the app can pass its run folder as `outputDir` for test runs and flows, and drop the copying in `src/main/runs/screenshots.ts`.
- Released in **0.18.0** (PR #69; version committed in #70). Wiki: Embedding → "Flows" bullet; Pages and browsers → "Upgrading to 0.18.0".

## 8. New in 0.19.0: seven more assertions (PRs #71–#73)

New matchers, in the framework, the step codec and the recorder toolbar. Gate project-side features on the capabilities `assertionMatchers` (`2` from 0.19.0; a number, so later matcher sets can raise it) and `pageAssertions`.

### What the step editor must render (the app's own codec copy, once it depends on `^0.19.0`)

- **`Expectation`** (step kind `expect`, which still has `locator`, `not`, `expectation`) gains:
  - `{ matcher: "toBeHidden" | "toBeEnabled" | "toBeChecked" }`: no value.
  - `{ matcher: "toHaveClass"; expected: TextMatcher }`
  - `{ matcher: "toHaveCSS"; name: string; expected: TextMatcher }`: a property name plus a value.
- **New step kind `expectPage`:** `{ kind: "expectPage"; not: boolean; expectation: PageExpectation }`, with `PageExpectation = { matcher: "toHaveURL" | "toHaveTitle"; expected: TextMatcher }`. It has **no locator**. Source: `await expect(page).toHaveURL("/checkout");`. Exported from `@itmetsam/samurai-framework/steps`.
- An editor that switches on `step.kind` or `expectation.matcher` needs a case for each. Until it has them, the safe fallback is to show these steps read-only, like `custom` ones.

### Semantics (for labels and help text)

- `toBeHidden`: no element, or not visible. `.not.toBeHidden()` means "visible".
- `toBeEnabled`: not `:disabled` and no `aria-disabled="true"`. This is the same check `click` and `fill` wait for. `.not.toBeEnabled()` means "disabled".
- `toBeChecked`: a checked checkbox or radio, or `aria-checked="true"`.
- `toHaveClass`: the whole class string, with whitespace collapsed on both sides, or a regex.
- `toHaveCSS`: the **computed** value (`rgb(255, 0, 0)`, not `red`). The name can be camelCase or kebab-case.
- A missing element never passes `toBeEnabled`, `toBeChecked`, `toHaveClass` or `toHaveCSS`, not even with `.not`.
- `toHaveURL`: a string starting with `/`, `./` or `../` resolves against the base URL exactly like `goto` does. Any other string must equal the full URL. A regex tests the full URL.
- `toHaveTitle`: compares trimmed text, or a regex.

### Recorder

- The Assert panel has new buttons: Hidden, Enabled, Checked, Has class and Has CSS. A button is only offered when it makes sense for the element. Has CSS refuses an empty value.
- New **Page** panel in the toolbar: URL or Title. The URL is prefilled **relative to the recording's `baseURL`** whenever it resolves back to exactly the current URL, so recorded tests pass on every environment.
- Recorded steps arrive as `RecorderEvent`s, as before: `expect` steps with the new matchers, and the new `expectPage` steps.

## 10. Answer to your hand-off `2026-10-26-test-outputs-and-inputs.md`: 0.21.0

Shipped in **0.21.0** (on npm 2026-10-26). PRs #77, #79, #81, #85, #86, #87. Everything in your section 2 is in, as decided. Below: what I designed (your section 4), the API for your section 5, and what changed or differs.

### Capabilities

`testInputsOutputs: true`, `flowPerBrowser: true`, `nodeFolder: 2`, `flowNodeFolders: 2`, `flowsApi: 3` (and `FLOWS_API` 3).

### Spec syntax (section 4)

```ts
test("purchase", { inputs: { email: "a@b.c" }, outputs: ["orderId", "ref"] }, async ({ page, inputs, outputs }) => {
  await page.getByLabel("Email").fill(inputs.email);
  await outputs.save("orderId", page.getByTestId("conf"), /Order #(\d+)/);
  await expect(page.getByTestId("conf")).toHaveText(/Order #(\d+)/, { output: "orderId" });
  await page.getByLabel("Ref").fill("gen-123", { output: "ref" });
});
```

- Options on `test`, `test.only`, `test.skip`, `test.fixme`: `{ reason?, inputs?: Record<string, string>, outputs?: string[] }`.
- **Name rules:** an identifier, and not `status`, `durationMs`, `error`, `__proto__`, `constructor` or `prototype`. The runtime, the codec and the toolbar share one check, `isIoName` in `./flows` core.
- **`outputs.save`** waits like a check, for non-empty trimmed text. A pattern saves its first group, else the whole match.
- **`{ output }`** works on `fill`, `toHaveText`, `toContainText`, `toHaveValue` and `toHaveAttribute`, never with `.not`.
- **A declared output that is never saved fails the test** with `output "x" was never saved`. A flow therefore never gets an empty value.
- **A test run on its own** uses each input's default.

### Section 5, row by row

- **A test's inputs and outputs without running it.**
  - `FoundTest.inputs?: { name; default }[]` (in declaration order) and `FoundTest.outputs?: string[]`, from `listTests`.
  - In the codec, `ParsedTest.inputs` / `outputs` have the same shapes.
  - Both are absent when the list is empty.
- **Codec steps and edits** (`./steps`):
  - New step: `{ kind: "saveOutput"; name; locator; pattern?: { source; flags } }`.
  - `fill.output?` and `expect.output?` (the four matchers only, never with `not`).
  - New text value: `{ kind: "input"; name }`, written as `inputs.name`.
  - New edit `{ op: "declare"; test; inputs?: { name; default }[]; outputs?: string[] }`. A list you pass replaces that list. Empty lists remove the options object; a `reason` stays.
  - Inserting or replacing a step that saves an output **declares it for you**.
  - A step that reads an undeclared input is **refused** with `applyEdit(): input "x" is not declared`. So for "Use as input": `declare` the input with its default first, then `replace` the fill.
  - `{ output }` on a negated check or another matcher, and bad names, are refused too, so the codec never writes code the runtime rejects.
  - **New unparsed reason:** `"dynamic-options"`, for an options object that isn't a plain literal.
- **Captured values:**
  - `TestSuccess` / `TestFailed` have `inputs?` (the values the test got, defaults included) and `outputs?` (what it saved; partial on failure). Both are absent when the test declares none.
  - In a flow, `NodeResult.inputs` holds the values a node was given.
- **Builder validation** (`./flows` core):
  - Pass `facts` to `checkFlow(flow, { …, facts })`, `scopeAt(flow, nodeId, env, { nodes, facts })` and `expressionProblems(flow, env, { nodes, facts })`. **Breaking:** the positional `nodes` argument moved into that options object.
  - Build the facts with `flowFactsFrom(await listTests(…), await listGroups(…))`. It takes the lists as they come, so you don't need any mapping code.
  - New problems: `<title>: input "x" has no source…`, `<title>: input "x": <expression problem>`, `<parallel title>: branches both save "x"`, `<title>: Group nodes can't set inputs ("x")` (errors) and `input "x" is not used by this test|node` (a warning).
  - Without `facts`, nothing new is reported.
- **Wiring for display:** `wiringAt(flow, nodeId, { facts })` returns `Record<input, InputWiring>`. `InputWiring` is one of:
  - `{ from: "node"; nodeId; output }`
  - `{ from: "expression"; expression }`
  - `{ from: "default"; value }`
  - `{ from: "none" }`
  
  The order is: override, then "use the default", then a node, then none. `alwaysBefore(flow, d, n)` is exported too.
- **Flow file shape:** Test and Group nodes have `inputs?: Record<name, { expression: string } | { useDefault: true }>`. Group nodes accept only `{ useDefault: true }`. The wiring is computed, never stored.
- **Expressions:** a keyed Test node's outputs are `nodes.<key>.<name>`, next to `status`, `durationMs` and `error`.
- **Once per browser** (breaking, `./flows/run`):
  - Every `FlowEvent` has `browser`. `flow-start` and `flow-end` come once per browser run. The last event is `{ type: "flow-done", status, runs }`, which has no `browser`.
  - `runFlowInProject()` resolves to `FlowRunResult = { status, runs: { browser, summary }[] }`.
  - New option `browsers?: SupportedBrowser[]` limits the runs.
  - Each node keeps the browsers it had: a Test node uses the project's, a Group node its group's. In a run for a browser the node doesn't use, it is `skipped` with `note: "not run in <browser>"`.
  - A failed run doesn't stop the next browser; an abort stops all.
  - The report (`result/flows/<id>.json`) has `runs[]`. The top-level `nodes`, `vars` and `error` moved into `runs[].summary`.

### Section 6: folders

- `nodeFolder(nodeId, browser)` returns `<browser>/nodes/<cleaned id>`. This is breaking: it now takes the browser.
- Screenshot paths in a node's events and results are relative to `outputDir`, for example `chrome/nodes/<id>/screenshots/…`. You can join `outputDir` and the path, and need `nodeFolder` only for display.
- Without `outputDir`, paths stay relative to `<project>/result`, as before.

### Recorder

- **Save as output:** a panel next to Assert, using the same pick flow. Name, plus an optional pattern.
  - It previews the value it would save, reading text the way `outputs.save` reads it.
  - It refuses a bad or reserved name (`name: "status" is reserved`), an invalid pattern, a pattern that doesn't match now, an element with no text, and an element that shows a secret.
- **Insert → input:** a third kind next to variable and secret, with a name and a temporary value.
  - It types the value, records `fill(inputs.name)` and declares the input with that value as its default.
  - Declared inputs show as a third group in the Insert list.
  - Inputs never go through the variable or secret stores.
- The recorder writes the spec file itself, including the declarations, so the app needs no change for recording.

### What differs or the app must change

- **Hand-typed outputs are gone:**
  - `FlowNodeModel.outputs` / `FlowNodeOutput` are removed; an old file's `outputs` is dropped on read.
  - The **node-definition flag `outputs?: boolean` is removed** too. `node-panel.tsx` reads `def.outputs` to show the hand-typed outputs panel. Delete that panel, and the `registry.test.ts` assertion on `outputs`.
- **`HandlerRun.runTests(nodeId, tests, onEvent)`:** custom handlers get one `browser` (`HandlerRun.browser`). The fourth argument is now `inputs`.
- **Outputs that contain a secret's value reach later nodes masked.** Results are masked before the flow reads them, so a wired value is the masked text. This is rare (a secret value appearing inside, say, an order reference), and the toolbar refuses to save an element that shows a secret.
- **Changed messages:**
  - An un-awaited page check is reported as `expect(page).toHaveURL() was not awaited`.
  - A reserved name in the toolbar gets `name: "x" is reserved`.
- **Not done in this version** (as agreed): non-text values, outputs from network, cookies or storage, Group node overrides and outputs, a CLI `--input` flag, and running a flow's browsers in parallel.
